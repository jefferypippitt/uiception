## Why this matters

`pnpm audit --prod` reports 17 advisories against this dependency tree, all
originating from a single pinned package: `next@16.1.7`. Of these, **8 are
HIGH severity** and remotely triggerable pre-auth on any deployed instance —
denial of service via Server Components, denial of service via connection
exhaustion in Cache Components, SSRF via WebSocket upgrades, and three
separate Middleware/Proxy-bypass variants (including one via dynamic route
parameter injection). 6 more are MODERATE (including a CSP-nonce XSS and a
`beforeInteractive` script XSS), and 3 are LOW. All are patched in Next.js
`16.2.5` or `16.2.6` — this is a same-minor-version bump, not a major
upgrade, so the fix is a version bump plus a build/smoke-test pass, not a
migration.

This is the single highest-leverage item found in the audit: no application
code needs to change, only the pinned dependency version.

## Steps

### Step 1: Bump `next` and `eslint-config-next`

Edit `package.json`:
- Change `"next": "16.1.7"` to `"next": "16.2.6"` (or the latest `16.2.x` patch available at install time — check with `pnpm view next versions --json` if you want the exact latest patch; any version `>=16.2.6` satisfies every advisory above).
- Change `"eslint-config-next": "16.1.7"` to the matching `16.2.6` (or same version chosen for `next`).

Then run:

```bash
pnpm install
```

**Verify**: exit 0, `pnpm-lock.yaml` shows `next` and `eslint-config-next` at the new version (`grep -A1 "^  next:" pnpm-lock.yaml`).

### Step 2: Confirm the advisories are gone

```bash
pnpm audit --prod
```

**Verify**: none of the 10 GHSA IDs listed in "Current state" above appear in the output. (Unrelated advisories on other packages, e.g. `postcss` or `@babel/core` transitive to `next`, may still appear or may be resolved incidentally by the bump — either is fine; they are out of scope for this plan.)

### Step 3: Typecheck and full check

```bash
pnpm typecheck
pnpm check
```

**Verify**: both exit 0. `pnpm check` runs `registry:validate` + `test:run` + `typecheck` — a Next.js patch bump should not change registry output or test results.

### Step 4: Production build

```bash
pnpm build
```

**Verify**: exit 0, no new build warnings referencing removed/changed Next.js APIs. Some of the patched advisories touch Cache Components, CSP nonces, and `beforeInteractive` scripts — if this repo doesn't use those features (check: no `cacheComponents` in `next.config.mjs`, no CSP nonce usage, no `beforeInteractive` `<Script>` strategy — confirm via `grep -rn "beforeInteractive\|cacheComponents" app/ next.config.mjs`), the bump should be a no-op behaviorally.

### Step 5: Manual smoke check

Since this is a static/no-backend site, run the dev server and confirm the homepage, a block category page, and the block preview route still render:

```bash
pnpm dev
```

Visit `/`, `/blocks/hero-section`, and `/view/hero-section-v1` (or any known versionId under `app/(preview)/view/[versionId]`). Confirm no console errors and pages render. Stop the dev server when done.

- `pnpm install` fails to resolve `next@16.2.6` (or later 16.2.x) — check for a typo in the version string before assuming a real resolution conflict.
- `pnpm build` fails with an error that traces to a genuine Next.js 16.2.x breaking change (unlikely for a patch release, but Next.js occasionally back ports behavior changes) — do not attempt to patch around a breaking change yourself; report the exact error.
- `pnpm audit --prod` still shows one of the 10 listed GHSA IDs after the bump — this would mean the version chosen didn't actually include the fix; re-check the chosen version against the "Patched versions" ranges above.
